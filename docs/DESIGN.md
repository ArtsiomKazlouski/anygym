# Трекер тренировок — схема данных и движок веса

Версия документа: v1-draft, 2026-09-14

## 1. Задача

Пользователь тренируется в трёх залах с разным оборудованием. Килограммы на грузоблоке
одного производителя не сравнимы с килограммами на другом (разные плечи рычага, трение,
единицы стека). Из-за этого:

- нет объективной прогрессии — вес «плавает» вместе с залом;
- каждая незнакомая железка настраивается заново на глаз → травмы;
- перерывы в 1–2 занятия сбивают самооценку нагрузки.

**Приложение отвечает на один вопрос: какой вес поставить прямо сейчас на этой железке,
как её настроить и сколько повторов сделать.**

Принцип: килограммы между моделями оборудования не пересчитываются никогда. Переносится
только относительная нагрузка — целевые повторы, запас (RIR) и шаг прогрессии.

## 2. Ключевые решения

| Решение | Выбор |
|---|---|
| Главная работа | Подсказка веса, а не просто журнал |
| Единица прогрессии | Упражнение (`exercise`), не зал и не железка |
| Идентификация железки | Вручную, со связыванием одной модели между залами |
| Фидбек | Повторы + 4 кнопки (маппятся в RIR) |
| Прогрессия | Двойная + авторегуляция между подходами |
| Анти-травма | Память настроек тренажёра, флаг боли, откат за паузу |
| Структура | Шаблоны в терминах паттернов + альтернативы + «занято» |
| Платформа | PWA, online-only (слой записи изолирован под будущий офлайн) |
| Стек | Next.js / Vercel / Neon Postgres / Auth.js + Google, allowlist |
| Фото | WebP ≤400px прямо в колонке БД |

## 4. Схема БД

Всё, кроме `pattern`, изолировано по `user_id`. Схема multi-user с первого дня,
доступ ограничен allowlist по email. Ниже — то, что реально лежит в базе после
миграций `0000`–`0006`.

### 4.1 Пользователи и справочники

Таблицы входа (`auth_user`, `auth_account`, `auth_session`,
`auth_verification_token`) заданы адаптером Auth.js и здесь не описываются.
Префикс `auth_` нужен, чтобы сессия входа не путалась с сессией тренировки.

    pattern(
      code          text pk,
      title         text not null,
      muscle_group  text not null,
      position      int  not null default 0
    )

### 4.2 Оборудование

`equipment_model` — личный каталог железок. Одна запись = один предмет, который
пользователь узнаёт в лицо. Может стоять в нескольких залах; паттерна у неё нет,
движение — свойство упражнения (см. 4.3).

    equipment_model(
      id            uuid pk,
      user_id       uuid fk -> auth_user,
      name          text not null,          -- "жим от груди Technogym, синий"
      brand         text,
      kind          enum('stack','plate_loaded','dumbbell','barbell','cable','bodyweight'),
      units         enum('kg','lb') not null default 'kg',
      step          numeric,                -- шаг прогрессии
      ramp_step     numeric,                -- шаг подводящих, если грубее (см. 5.1)
      min_weight    numeric,
      max_weight    numeric,
      ladder        numeric[],              -- явный ряд весов (гантели)
      bar_weight    numeric,                -- вес грифа (штанга)
      photo         bytea,                  -- WebP, длинная сторона <= 400px
      photo_mime    text,
      notes         text,
      created_at    timestamptz not null,
      updated_at    timestamptz not null
    )

    gym(
      id            uuid pk,
      user_id       uuid fk -> auth_user,
      name          text not null,
      note          text,
      is_active     boolean not null default true,
      created_at    timestamptz not null
    )

`gym_equipment` — экземпляр модели в конкретном зале и переопределения сетки:
тот же модельный ряд бывает со стеком в фунтах, а гантельный ряд у каждого зала
свой. Пустое поле означает «как у модели», а не ноль.

Единицы нельзя переопределить в одиночку: границы и шаг модели записаны в её
единицах и, оставшись, были бы прочитаны как чужие — сетка молча поехала бы.
Поэтому смена единиц требует задать шаг, минимум и максимум в новых единицах
(либо ряд весов, который задаёт сетку целиком).

    gym_equipment(
      id                 uuid pk,
      gym_id             uuid fk -> gym,
      equipment_model_id uuid fk -> equipment_model,
      location_note      text,              -- "у окна, второй ряд"
      units_override     enum('kg','lb'),
      step_override      numeric,
      ramp_step_override numeric,
      min_override       numeric,
      max_override       numeric,
      ladder_override    numeric[],
      is_active          boolean not null default true,
      created_at         timestamptz not null,
      unique(gym_id, equipment_model_id)
    )

`equipment_setup` — запомненные настройки. По умолчанию на модель (разметка
сиденья одинакова на одинаковых железках), при необходимости переопределяются
для экземпляра в конкретном зале.

    equipment_setup(
      id                 uuid pk,
      user_id            uuid fk -> auth_user,
      equipment_model_id uuid fk -> equipment_model,
      gym_equipment_id   uuid fk -> gym_equipment,   -- null = настройка на модель
      settings           jsonb not null default '{}',
      note               text,
      updated_at         timestamptz not null,
      unique(user_id, equipment_model_id, gym_equipment_id)
    )

### 4.7 Фото железки

Лежит в `equipment_model.photo` (bytea) рядом с остальными полями модели.
Нужно не для красоты: это способ узнать в новом зале, что тренажёр тот же
самый, — а без узнавания не работает перенос истории между залами.

**Сжимает браузер, а не сервер.** Снимок с телефона — 3-5 МБ; гнать их наверх,
чтобы уменьшить там, значит платить трафиком в зале, где связь и так так себе.
Перед отправкой картинка ужимается до 400px по длинной стороне и переводится
в WebP, на выходе 60-100 КБ. Поворот берётся из EXIF, иначе снятое боком фото
ляжет повёрнутым.

**Байты не ездят вместе с моделью.** `select()` тянет таблицу целиком, поэтому
все запросы берут явный список колонок без `photo` (`MODEL_COLUMNS`), а наличие
фото отдают флагом. Сами байты идут отдельным маршрутом
`/equipment/[id]/photo`, закрытым той же проверкой входа, что и всё остальное.

Адрес несёт версию — `?v=updatedAt`, — поэтому кэшируется навсегда: поменял
фото, поменялся и адрес.

### 4.3 Упражнения

**Ключ прогрессии — упражнение, а не железка.** На одних и тех же гантелях
делаются жим под 45°, жим под 30°, бицепс и молоточки; рабочие веса у них
разные, и слипаться их истории не должны. По той же причине не нужно
отдельно моделировать односторонние движения: «разгибание ног по одной» —
просто другое упражнение со своим весом.

    exercise(
      id                  uuid pk,
      user_id             uuid fk -> auth_user,
      name                text not null,     -- "жим гантелей под наклоном 45°"
      pattern_code        text not null fk -> pattern,
      equipment_model_id  uuid not null fk -> equipment_model,
      target_reps         int not null default 12,   -- цель повторов (см. 5.4)
      notes               text,
      is_active           boolean not null default true,
      created_at          timestamptz not null
    )

Заявленного рабочего веса у упражнения нет намеренно. Такое число нужно
угадать заранее, вне зала, — ровно то, от чего приложение должно избавлять.
И оно статично: вписал 36 в сентябре, за месяц дошёл до 26, а в поле всё ещё 36.

Вес первого подхода нового упражнения вводится руками, стоя перед железкой,
где его можно почувствовать. Дальше ведёт история.

### 4.4 Шаблоны

Пункт шаблона написан в терминах паттерна, а не железки — иначе он не
переносится между залами.

    template(
      id          uuid pk,
      user_id     uuid fk -> auth_user,
      name        text not null,
      is_active   boolean not null default true,
      created_at  timestamptz not null
    )

    template_item(
      id                    uuid pk,
      template_id           uuid fk -> template,
      position              int not null,
      pattern_code          text not null fk -> pattern,
      preferred_exercise_id uuid fk -> exercise,      -- привычное упражнение
      excluded_exercise_ids uuid[] not null default '{}',
      scheme                enum('straight','ramp') not null default 'straight',
      sets                  int not null default 3,   -- для straight
      ramp_percents         numeric[],                -- для ramp: доли от верха
      note                  text
    )

Список альтернатив не хранится: он вычисляется как «все упражнения этого
паттерна, чья железка есть в текущем зале», минус `excluded_exercise_ids`
и минус те, у которых в этой же тренировке есть собственный пункт. Порядок:
`preferred_exercise_id` → остальные по убыванию объёма истории.

### 4.5 Тренировки

    workout_session(
      id           uuid pk,
      user_id      uuid fk -> auth_user,
      gym_id       uuid fk -> gym,
      template_id  uuid fk -> template,      -- null = тренировка без плана
      started_at   timestamptz not null,
      ended_at     timestamptz,              -- null = идёт прямо сейчас
      note         text
    )

    session_item(
      id                uuid pk,
      session_id        uuid fk -> workout_session,
      position          int not null,        -- меняется при «занято»
      template_item_id  uuid fk -> template_item,  -- null = добавлено на ходу
      pattern_code      text not null fk -> pattern,
      exercise_id       uuid fk -> exercise, -- null, пока не выбрано
      status            enum('pending','active','done','deferred','skipped'),
      target_sets       int not null,
      extra_sets        int not null default 0,    -- добавленные на тренировке
      rep_min           int not null,
      rep_max           int not null,
      deferred_count    int not null default 0
    )

    set_log(
      id                   uuid pk,
      session_item_id      uuid fk -> session_item,
      position             int not null,
      kind                 enum('warmup','ramp','working') not null default 'working',
      weight               numeric not null,   -- как написано на стеке
      units                enum('kg','lb') not null,
      weight_kg            numeric not null,   -- нормализовано, вся математика тут
      reps                 int,
      feedback             enum('easy','on_target','limit','failed'),
      pain_zone            text,
      prescribed_weight_kg numeric,            -- что предложил движок
      prescription_source  enum('history','declared','probe','manual','deload','pain_backoff'),
      logged_at            timestamptz not null
    )

`prescribed_weight_kg` и `prescription_source` хранятся не для интерфейса,
а чтобы потом честно оценить, насколько движок угадывает.

Удаление каскадное: тренировка уносит свои пункты, пункт — свои подходы.

### 4.6 Производное состояние

Отдельной таблицы состояния прогрессии нет, всё выводится из `set_log`:

- **рабочий вес упражнения** = `weight_kg` последнего `working`-подхода по этому
  `exercise_id`, **который не был провален**. Рост внутри сессии (50 → 55
  по фидбеку «легко») должен переноситься, а финальный проваленный подход
  не должен опускать базу дважды — за него уже отвечает межсессионная
  прогрессия из 5.4;
- **дата последней работы на паттерн** = максимальный `logged_at` среди
  `working`-подходов, чей `session_item.pattern_code` совпадает;
- **заморозка по боли** = был ли `pain_zone` в последних двух сессиях
  на этом упражнении.

Подводящие подходы (`kind = 'ramp'`) и разминка в прогрессии не участвуют.

## 5. Движок веса

Вся математика в `weight_kg`. Отображение — в единицах железки.
Схемы подходов — в 5.7; всё остальное в разделе описывает назначение
**рабочего** веса, который для рампы означает верхний подход.

### 5.1 Дискретизация

    round_to_available(w_kg, gym_equipment) -> достижимый вес

Берёт `ladder_override ?? ladder` если он задан (гантели), иначе `step`/`min`/`max`
с учётом override экземпляра. Для штанги сетка отсчитывается от веса грифа.
Движок не имеет права назвать вес, которого на этой железке физически нет.

Направление округления:

| Случай | Направление |
|---|---|
| Рост на ступень | вверх (следующая ступень сетки) |
| Снижение на ступень | вниз |
| Назначение веса: разведка, откат, снижение по боли | к **ближайшей** ступени |
| Разминочный подход | вниз |

Ближайшая, а не строго вниз — потому что на грубой сетке строгое округление вниз
искажает замысел: шаг 20 кг при рабочих 100 превратил бы откат в −20% вместо
запрошенных −5%. Отсюда следствие, принятое сознательно: **если запрошенное снижение
меньше половины шага, сетка его не выражает и вес остаётся прежним.** Это безопасно —
один подход с фидбеком «легко» и так вернул бы вес на то же место.

Поверх этого действует страховка: назначенный вес никогда не превышает опорный.
Она срабатывает только если опорный вес не лежит на текущей сетке — история пришла
с экземпляра с другим шагом или в других единицах.

**Грубый шаг для подводящих.** Шаг отвечает за две разные задачи: точность прибавки
при прогрессии и округление подводящих подходов. Рабочему весу точность нужна,
подводящему — нет: вешать 82.5 ради разминки значит возиться с блинами по 1.25
на каждой стороне. Поэтому у модели есть `ramp_step`; подводящие и разминка
округляются по нему, рабочий вес — по обычному `step`. У штанги это даёт
20, 60, 80, 90 и верх 102.5.

**Список достижимых весов.** Из той же сетки строится барабан выбора веса в форме
записи подхода: выбрать вес, которого на железке нет, невозможно в принципе.
Если сетка не задана, остаётся ручной ввод.

**Ноль — допустимый вес.** Подтягивание без отягощения это ноль, а не отсутствие
подхода. Турник, на который иногда вешают блины, описывается как `plate_loaded`
с минимумом 0: ноль означает свой вес, остальное — добавку, и прогрессия
работает обычным образом. Тип `bodyweight` оставлен для случая, когда
отягощение не используется никогда: сетки у него нет, расти можно лишь
в повторах.

### 5.2 Маппинг фидбека

| Кнопка | Значение | RIR |
|---|---|---|
| Легко (мог ещё 3+) | `easy` | ~3 |
| В точку (ещё 1–2) | `on_target` | ~1.5 |
| На пределе | `limit` | 0 |
| Не добил | `failed` | < 0 |

### 5.3 Назначение веса на первый рабочий подход упражнения

    1. База
       a. Есть история по этому упражнению:
             W = рабочий вес упражнения
             source = 'history'
          Применить межсессионную прогрессию (см. 5.4).
       b. Истории нет, но есть другое упражнение того же паттерна:
             base = его рабочий вес
             W = 0.6 × base
             source = 'probe'
          UI показывает, от какой железки считается, и даёт сменить базу
          или покрутить процент.
       c. Ничего нет:
             ручной ввод, source = 'manual'

    2. Откат за паузу (только для ПЕРВОГО упражнения на данный ПАТТЕРН в сессии)
       d = дни с последней работы на этот паттерн (не на это упражнение)
       d <= 10  -> × 1.00
       11..21   -> × 0.95
       22..42   -> × 0.90
       43..90   -> × 0.85
       d > 90   -> сброс: история устарела, идти по ветке 1b
       source = 'deload' если множитель < 1

    3. Откат за боль
       Если в последних двух сессиях на этом упражнении был pain_zone:
             W = W × 0.9, source = 'pain_backoff'
             UI показывает: "в прошлый раз была боль: <зона>"
       Межсессионный рост при этом заморожен (см. 5.4).

    4. W = round_to_available(W, gym_equipment)   -- к ближайшей ступени,
                                                  -- но не выше опорного веса

**Целевые повторы — свойство упражнения, а не плана.** «Тяга гантелей —
двенадцать» верно в любом плане и в любом зале; то, что вышло десять, —
результат, а не другая цель. Поэтому `target_reps` живёт на `exercise`,
а у пункта плана полей повторов нет вовсе.

Одно число и на подводящих, и на верхнем подходе: подводящий отличается весом,
а не тем, сколько раз ты собираешься поднять. Отдельных повторов по ступеням
рампы больше нет.

**Диапазон выводится, а не вводится.** Движку нужны две границы: пока повторы
растут внутри, вес стоит, а закрыл верх — прибавился. Без буфера прогрессия
становится линейной, то есть каждый раз либо плюс вес, либо ничего, и потолок
приходит быстро. Нижняя граница считается как `target_reps − 2`, наружу
не показывается и всплывает только в пояснении, когда вес снижается.

Пункт сессии хранит границы снимком: изменение цели не должно задним числом
переписывать уже проведённые тренировки.

### 5.4 Межсессионная прогрессия

Смотрим рабочие подходы прошлой сессии по этому упражнению:

    провалена половина подходов и больше  -> W -= step
    провален хоть один                    -> W без изменений
    во всех закрыт верх диапазона         -> W += step
    иначе                                 -> W без изменений (растём в повторах)

Заморожено, пока действует откат за боль.

**Между тренировками решают повторы, а не кнопка.** Раньше ответ «на пределе»
хоть на одном подходе блокировал прибавку — и прогресс становился невозможен:
последний подход на верхней границе диапазона почти всегда ощущается
предельным, в этом и смысл границы. Пользователь делал 15, 15, 15 при цели 15
и стоял бы на одном весе бесконечно.

Кнопка по-прежнему правит вес внутри тренировки (5.5) — там она к месту.

### 5.5 Авторегуляция внутри упражнения

По фидбеку **предыдущего** подхода:

    easy       -> W += step
    on_target  -> W без изменений
    limit      -> W без изменений, пометить "не растить в следующей сессии"
    failed     -> W -= step
    pain_zone  -> стоп: предложить −2 шага либо завершить упражнение

Отмена отката за паузу: если первый подход после паузы получил `easy`, следующий
подход возвращается к **доотка́тному** весу, а не к «откаченный + шаг». Откат — это
разведка, а не наказание.

### 5.6 Разминка

Отдельных разминочных подходов нет намеренно.

Разминка нужна по сути в одном движении — штанге, — а там её роль уже играет
рампа: гриф, 60, 80, 90 и есть подводка. В остальных упражнениях пользователь
сильно не разминается. Держать ради одного случая отдельный вид подхода,
правило «первое упражнение на мышечную группу в сессии» и связанную с ним
бухгалтерию оказалось дороже пользы.

Мышечная группа в таксономии паттернов остаётся: она нужна для «давно
не делал».

Значение `warmup` в `set_kind` сохранено — по нему читаются старые записи,
но новых не появляется.

### 5.7 Схемы подходов: прямая и рампа

Прямая схема — один рабочий вес на все подходы, корректируется фидбеком между
подходами. Рампа — восходящая пирамида к верхнему подходу:

    гриф -> 60 -> 80 -> 90 -> 100

Ключевое: **в рампе рабочий подход один — верхний.** Подводящие имеют
`kind = 'ramp'`, в прогрессии не участвуют и считаются от верхнего веса
процентами из `ramp_percents`. Фидбек, межсессионная прогрессия, откат за паузу
и снижение по боли — всё висит на верхнем подходе.

Почему это важно, а не косметика: когда вес верхнего подхода выбирается на
ощущение, потолок задаётся не силой, а осторожностью, и потому не двигается.
Рампа превращает потолок в число, которым управляет обратная связь.

Две поправки, без которых схема ломается на практике:

- **Подводящая ступень обязана быть строго выше предыдущей и строго ниже
  верхней.** На грубой сетке доли схлопываются: 0.85 и 0.9 от 100 при шаге 20
  дают 80 и 100. Схлопнувшиеся ступени выбрасываются.
- **Разминка отдельным подходом не добавляется**, если рампа сама начинается
  ниже `WARMUP_FACTOR` от верха — она и есть разминка. Добавляется только когда
  рампа стартует высоко.

**Пересчёт под фактический вес.** Веса в форме редактируемые. Если ты поставил
не то, что предложено, остаток рампы едет пропорционально: поставил 88 вместо 80 —
дальше не 90 и 100, а 100 и 110. Ступени ниже `RE_ANCHOR_MIN_PERCENT` (0.5) ничего
не пересчитывают: подход пустым грифом не говорит о том, каким будет твой верх.

**Срезание рампы по ходу.** Если подводящий подход дался тяжелее ожидаемого,
запланированный верх сегодня недостижим:

    'не добил' на подводящем  -> верхний подход отменяется
    'на пределе' на подводящем -> верх срезается до одной ступени выше текущей;
                                  рабочий подход остаётся всегда, иначе прогрессии
                                  не за что зацепиться

Поэтому фидбек спрашивается и на подводящих подходах: без него срезание рампы
мертво. В прогрессии подводящие всё равно не участвуют — она смотрит только на
`kind = 'working'`.

### 5.8 Интервал между подходами

Таймера отдыха нет намеренно: пользователь следит за отдыхом по часам и
ориентируется не на время, а на пульс. Но интервал приложение знает бесплатно —
метка времени ставится на каждую запись подхода.

Подпись говорит «через 1:40», а не «отдых 1:40»: отметка ставится в конце
подхода, поэтому в промежуток входит и отдых, и сам следующий подход.
Приложение не должно называть величину точнее, чем умеет её измерить.

Величина нужна не для дисциплины, а как первый подозреваемый, когда повторы
сыплются от подхода к подходу: из литературы это самый доказанный рычаг
(см. раздел 12).

## 6. Примеры «вход → выход»

**Пример 1. Знакомая железка, штатный рост.**
Жим в тренажёре Technogym, диапазон 8–12, шаг 5 кг.
Прошлая сессия: 50×12 easy, 50×12 on_target, 50×12 on_target. Пауза 4 дня.
→ Все подходы на rep_max, без limit/failed → W = 55. Откат не применяется.
→ Разминка (первое упражнение на грудь): 30 кг × 8–10.
→ Подсказка: **55 кг, цель 8–12**. После первого подхода 55×9 on_target → второй тоже 55.

**Пример 2. Незнакомое упражнение в новом зале.**
Тяга верхнего блока, истории нет. Есть история по `vertical_pull` на
другом тренажёре: рабочий 60 кг. Шаг нового — 5 кг.
→ W = 0.6 × 60 = 36 → round вниз = 35.
→ Подсказка: **35 кг — разведка, база: «тяга верхнего блока, зал Б, 60 кг».
Сделай 8 и отметь, как было.**
Результат 35×8 easy → второй подход 40. Снова easy → 45. on_target → рабочий найден.

**Пример 3. Пауза 30 дней.**
Жим ногами, рабочий 120 кг, шаг 10 кг, последняя работа на `squat` 30 дней назад.
→ Множитель 0.90 → 108 → ближайшая ступень = 110. Плюс дополнительный разминочный подход.
→ Подсказка: **110 кг (−10% после перерыва 30 дней), цель 8–12.**
Первый подход 110×12 easy → второй возвращается к **120**, не к 120+10.

**Пример 4. Боль.**
Сведение, 40 кг, второй подход отмечен болью в плече.
→ Упражнение предлагается завершить. Прогрессия по нему заморожена.
→ Следующая сессия: 40 × 0.9 = 36 → round вниз = 35, с предупреждением
«в прошлый раз была боль: плечо». Рост не возобновится, пока две сессии подряд
не пройдут без боли.

## 7. Автомат сессии

    любой    --тап по пункту-->   active     (прежний активный -> pending)
    active   --записал подходы-->  done       (кнопкой «Дальше»)
    active   --"занято"-------->   deferred   (position -> в конец)
    любой    --сессия закрыта-->   skipped    (всё незакрытое разом)

Отдельной кнопки «пропустить» нет намеренно. Она соседствовала с «занято»,
и по звуку подходила лучше — человек жал её, желая вернуться позже, а пункт
закрывался насовсем. Пропуск теперь означает одно: ты завершил тренировку,
не дойдя до него.

Перейти можно к любому пункту тапом. Это же заменяет и перестановку упражнений
местами: порядок в зале не совпадает с планом, а таскать пункты в списке
на потной сенсорной панели — занятие на любителя.

Пункт со статусом `deferred` предлагается повторно при закрытии тренировки.

## 8. Границы

Приложение — личный журнал и калькулятор нагрузки. Флаг боли собирает историю для
тебя и для разговора с врачом; это не диагностика. Приложение не заменяет тренера
и не оценивает технику.


## 9. Не входит в v1

Графики и аналитика прогресса (только плоская история), офлайн-режим, распознавание
тренажёров по фото, контроль недельного объёма по мышечным группам, раскладка блинов
для штанги, маршрут по залу с учётом занятости, таймер отдыха.

(Фото тренажёра сделано, см. 4.7.)

### Отложено до условия

Не «когда-нибудь», а по конкретному признаку — чтобы не всплывало в каждом
разговоре и не забылось.

| Что | Когда возвращаться | Почему не сейчас |
|---|---|---|
| Экспорт истории в JSON | после ~20 настоящих тренировок | данных пока на одну тренировку; терять нечего, а от потери самих данных защищает снимок базы |
| «Давно не делал» | когда появится несколько дней недели и история по ним | с одним планом и одной тренировкой подсказка будет говорить очевидное |

Экспорт защищает не от потери данных, а от потери **доступа**: снимок Neon
бесполезен, если Neon однажды закроет бесплатный тариф или понадобится
переехать. Поэтому он нужен, но позже — когда в базе будет что вывозить.

## 11. Открытые вопросы

- ~~Односторонние упражнения (одна рука / одна нога)~~ — **решено: отдельного
  моделирования не нужно.** Подход делается сразу на обе стороны, меняется
  только вес. Поскольку прогрессия висит на упражнении, «разгибание ног
  по одной» — это просто другое упражнение со своей историей и своим рабочим
  весом. Ни флага на подходе, ни отдельного паттерна, ни удвоения объёма.
- Дроп-сеты и отказные подходы — сейчас не моделируются; `failed` их частично
  покрывает.
- Коэффициент разведки 0.6 взят как заведомо безопасный. После нескольких десятков
  реальных разведок по `prescribed_weight_kg` vs фактический рабочий вес его можно
  будет откалибровать по своим данным.


## 12. Что говорит литература

Выжимка сделана по ходу работы, когда вставали вопросы «а как правильно».
Влияет на дефолты, но ничего не навязывает: цели выбирает пользователь.

**Диапазон повторов почти не влияет на рост мышц.** Низкие нагрузки (≤60% от
максимума, много повторов) и высокие дают сопоставимую гипертрофию, если подходы
доводятся близко к отказу. Прирост силы в одноповторном максимуме достоверно
выше у тяжёлых нагрузок.

**Близость к отказу: кривая выполаживается около 2 повторов в запасе.** Рост
мышц усиливается по мере приближения к отказу, но после ~2 RIR прибавка почти
исчезает. Для силы связь с близостью к отказу незначима.

**Цена отказа — травмы.** Отказные подходы повышают риск через разрушение
техники и добавляют 24-48 часов к восстановлению. Отказ уместнее на тренажёрах
с фиксированной траекторией, чем на тяжёлых базовых движениях со свободным весом.

**Отдых — самый доказанный рычаг.** Три минуты против одной дают больше и силы,
и мышц. Отсюда 5.8: когда повторы падают, первое, что стоит проверить, — это
интервал, а не вес.

**Способ прогрессии вторичен.** Растить вес при фиксированных повторах или
растить повторы при фиксированном весе — при равном объёме и равной близости
к отказу результат одинаковый. Значит «снизить вес» и «снизить повторы» при
недоборе примерно равноценны, и выбирать надо по сохранности техники.

Источники:
Schoenfeld и др., низкие vs высокие нагрузки, JSCR 2017;
Robinson и др., близость к отказу, Sports Medicine 2024;
Grgic и др., отказ vs не-отказ, JSHS 2021;
Schoenfeld и др., длина отдыха, JSCR 2016;
Plotkin и др., прогрессия весом vs повторами, PeerJ 2022.
